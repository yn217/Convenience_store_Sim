# 品質・テスト・リリース判定計画 v0.1
更新: 2026-10-22

## 原則
- コード上の関数をなぞるテストだけでなく、**プレイヤーが起こす一連の現象**を検証する。
- GDScriptドメイン単体・データ契約/Schema・表示Scene/操作・フル営業シナリオを分離。全E2Eを毎回走らせない。
- ローカルで実行可能なheadlessテストと目視シーン試験。GitHub Actionsは導入しない。
- 実測の際はOS/Godot版/CPU/GPU/解像度/ズーム/マップ/什器数/客数/試行回数を記録。**テスト条件縮小による見かけ改善を禁止**。

## 2. 自動テストの層
- **Pure-domain**: グリッド回転4方向、到達性、Lot FEFO、予約/会計の冪等性、価格スナップショット、損益/現金、広告日境界、ランダムseed再現性。
- **Asset contracts**: マニフェストのrotation画像4枚、RGBA、pixel anchor、footprintとaccess sides整合、slot overlay参照、パス、ライセンス台帳。
- **Scene smoke**: 店舗表示、ズーム/パン、配置、選択、オーバーレイ、変更→表示反映。
- **Scenario/E2E**: S-01〜S-16の代表シナリオ。UIが必須の項目は録画/スクリーンショット等の再現手順も可。
- **Save compatibility**: 旧Schema読込拒否/移行、破損時のリカバリ、保存失敗時に元ファイルが壊れないこと、ロード直後の日次イベント重複なし。
- **Visual regression**: 画風基準3種、四方位、ズーム0.5/1/2、空/中/満、客との前後関係。画像差分に加えて目視も実施。

## 3. 固定ベンチマークの報告フォーマット
- 初期ベンチ条件は**暫定**: 16×12タイル、什器20基、可視客30人、1920×1080、ズーム1.0、ゲーム速度1×、1分間計測。
- 記録: test scene/seed, OS, GPU, CPU, Godot版, 実行ビルド/commit, 事前ウォームアップ, FPS median/p95 frame time, CPU/GPU/メモリ使用, frame stutters, draw calls。
- 予算案: 60fpsターゲットなら1frame約16.7ms。ただし正式SLOは**ベースライン実測後に明文化**。未計測で「達成」と主張しない。
- 計測でキャラ数/商品表示段階を減らす場合は**別条件として報告**し、同条件比較に混ぜない。

## 4. Issueを閉じる条件
- [ ] スコープ、入力、出力、非対象が実装で守られている。
- [ ] 仕様の不変条件がunit/integrationで確認できる。
- [ ] プレイヤー操作が伴う機能では、実際のUIで確認した。
- [ ] 仕様との差分/意図的な簡略化/未完了の例外を記録した。
- [ ] 新規発見の欠陥をIssue化して参照を残した。
- [ ] 重要なデータ競合/負在庫/二重会計/セーブ破損が未解決ならcloseしない。

## 5. QA担当の観点
- ゲーム性: 来店→買物→レジ→利益を感じられるか。営業不可から復帰できるか。
- 3D→2Dアセット品質: フットプリント、4方向、ガラス透過、商品差替、客の重なり、色調統一。
- 経済: 広告費の費用対効果、廃棄に意味があるか、資金枯渇に説明があるか。
- 性能: 描画と経路探索とシミュレーションtickをプロファイラで分けて特定できるか。
- UI: 誤クリック、見えない操作領域、重なり、説明不足、スクロール、文字切れ。
- 運用: 旧バージョンのセーブ、破損ファイル、パッケージ化、再配布可能な素材。
