# 2Dアセット制作・投影・什器形状 実装詳細仕様 v1.0

更新: 2026-10-29 / 対象: 新規ChatGPT/Codex生成の店内2D什器、商品一体型候補、プロップ。
状態: **仕様確定（候補の画像品質・ランタイム実装は未承認）**。Issue #102/#123/#157/#163、Draft PR #164に従う。

## 1. 目的・優先順位・旧3D仕様との整合

- **ゲームで使う素材は2D画像**。新規アート制作の必須前提としてBlender/3Dモデル化を要求しない。SVG/レイヤー付き2D/AI生成RGBA/手描き画像を許可する。過去のBlender素材を削除せず、旧仕様はレガシー実装・参考資料として保持。
- 実世界座標・ズーム・4方位・接地点・当たり判定の**数値契約は変更しない**。正本: [02_GRID_AND_ASSET_CONTRACT](../implementation/02_GRID_AND_ASSET_CONTRACT.md) と \`scripts/presentation/iso_projection.gd\`。
- 制作上の優先: **正しい日本の什器型式 > ゲームの投影/寸法 > 適切な商品形状と向き > アート品質 > 画素解像度**。誤った屋根や商品分類を美化して完成扱いにしない。
- **出力は描画レイヤー用の素材候補**。ImageGen画像単体に「4方向可」「実寸一致」「ゲーム動作確認済み」と付けることは禁止。QAを通過した後に正式runtime manifestへ昇格する。
- 本書は新しい2D素材の**アート制作工程**に関して旧 \`ASSET_PRODUCTION_SPEC.md\` のBlender必須部分を置換する。ゲームエンジン・Domainのシミュレーション・既存Manifestの契約は勝手に上書きしない。

## 2. 厳密な2:1投影と画像生成プロンプトの限界

ゲームの正投影式（世界単位は1tile=1.0m、座標原点はセル(0,0)中心）:

\`\`\`text
screen_u = origin_u + zoom*(64*(x-y))
screen_v = origin_v + zoom*(32*(x+y) - 78.38367177*z)

source_u = 128*(x-y)
source_v = 64*(x+y) - 156.76734354*z
\`\`\`

- \`+X\` 1mはsource \`(+128,+64)\`、\`+Y\` 1mはsource \`(-128,+64)\`、\`+Z\` 1mはsource \`(0,-156.76734354)\`。ズーム1のscreen値は各1/2。
- 地面の軸の画面傾斜は**+Xが+0.5、+Yが-0.5**（画面左→右に辿ると+Y方向を逆向きに見る）。「45°カメラ・30°仰角」のプロンプトだけでは数式一致にならない。
- source画像に**複数の測定可能な制御点**（少なくとも接地点1つと、異なるworld XY上の2本の辺の両端、背面の上端/高さ）をアート外のQA companion JSONに記録する。食品の絵や影の端を制御点に使わない。
- 期待点を\`P_world\`、対応する実測画像座標を\`P_source\`、crop前原点と平行移動を\`T\`とし、\`r_i=P_source_i - (P_iso(P_world_i)+T)\`で誤差計測。**均一な平行移動/等方スケールで補正できない軸角度・遠近収束はFAIL**。画像をXだけ拡大・Yだけ圧縮する補正は禁止。
- 校正対象のX/Y辺端点差分は **±1 source px/軸**、高さは **±2 source px**、ゲームの接地点はzoom1で **±1 screen px** を既存の契約に合わせる。自動検査できないAI一枚絵は\`projection_verified:false\`のまま。
- 一枚絵の角度が合わない場合は **再描画・透視補正可能な原画の部品別再構成・独立2Dレイヤーでの再制作**。日本語ラベルが左右反転するミラーは禁止。
- \`r=0,1,2,3\` の4向きを**別に制作・校正**。単なる画像90°回転では立面/奥行/遮蔽が一致しない。段階的にr0だけを生成してよいが、レビュー完了とruntime採用を混同しない。
- \`r0\`の1×2什器は長辺E（world+X側）が販売正面。r1でS、r2でW、r3でNにアクセス面も回転。商品ラベルは回転後も実際の客側の面を向ける。どんぶり型カップ麺は**フタを主役にせず側面正面ラベルを表示**。
- 回転後の足元\`origin_tile\`、\`footprint\`、アクセスセル、床輪郭の計算は02の座標式を必ず使う。画像のalpha bboxから当たり判定を計算しない。

## 3. 什器型式と絶対禁止事項

| family | 最上部構造 | 商品形状/アクセス | 即FAIL例 |
|---|---|---|---|
| \`AMBIENT_GONDOLA_OPEN\`（菓子/パン/汎用/カップ麺） | **薄い最上販売棚板のみ**。上を覆う大きな屋根、厚い無地天板、上部キャビネット禁止 | 浅い棚板・細い支柱・前縁レール。袋、箱、どんぶりを商品として描き、販売面を開放 | 「CANONICAL EMPTY」の巨大天板を保持、立方体商品を等間隔に並べる |
| \`CHILLED_OPEN_FRONT\`（おにぎり/弁当/デザート/サンドイッチ） | 冷却装置に必要な薄い照明・枠は可 | 食品種類に応じた透明パック/トレー/三角おにぎりを正面表示。冷気吹出口・ガラスは実売場型式に照合 | 飲料ケースの流用、巨大屋根、商品を前縁で覆う |
| \`CHILLED_GLASS_DOOR\`（飲料等） | 冷却キャビネット躯体/天枠は**合法** | 内部商品→扉→ハイライト。扉開閉・通路アクセスを検査 | ガラス反射を商品の前後関係より優先、ドア部分を単一不透明画像 |
| \`FREEZER_CHEST\` | 実機のガラス天蓋は可 | 上面から商品を取り出す。独立した開閉面と陳列槽 | 常温ゴンドラの屋根判定を誤適用 |
| \`HOT_COUNTER_SINGLE\`（卓上おでん/肉まん） | 実機の小型カバー/保温フタは可 | おでんは出汁・仕切り・大根/卵/こんにゃく/ちくわ等。保温設備を小型独立物として描く | 冷蔵売場や3連大型ケースを「単体鍋」として登録 |
| \`HOT_MULTI_BAY\`（3連ホットスナック/大型おでん） | 各区画の加温カバー可 | 商品を複数の加温区画に分け、長さと取出し側を設計 | 既存1×1/1×2へ画像を歪めて押し込む |
| \`EXTERIOR_COMPOSITE\`（植栽/塀/背景群） | 大型一体2Dレイヤー可 | **タイルに分割せず**長い背景シルエットと連続植栽を1つのシーン/アトラスで扱う | タイル境目が見える反復柄、「Minecraft」状の道路/植栽 |

- 常温棚用の古い \`roof付きEMPTY\` を\`strict reference\`として流用してはいけない。\`EMPTY\`の構造QAがPASSするまでは\`FULL\`量産禁止。
- 商品画像は**単品箱の3D押出し/紙箱化**を禁止。実売場の包装形状に一致させる。生成が別の商品になったら実際の品種で「未承認候補」に分離し、要求品種に改名してはならない。
- 使い回しのAI文字・実在ブランド・出典不明の画像はゲームの正式販売データや権利承認に流用しない。ラベルの意味・価格はDomainデータが正本。

## 4. 占有寸法と大型設備の扱い

- 既存 \`data/fixtures/mvp_v1.json\` の \`footprint\` と \`dimensions_m\` を**既存設備の正本**とする。既存1×2は物理最大0.92×1.92m、1×1は最大0.92×0.92m（いずれも既存定義に従う）。
- 3連・4連の生成画像に **新しい\`fixture_type_id\`と適切な複数タイルfootprint** を与える。**ゲーム内サイズ未測定の候補には\`footprint:null\`を保持し、runtime登録を禁止**。画像アスペクト比から占有タイルを自動決定してはいけない。
- 論理occupancyは見た目ではなくDomain定義で決定。world外形は各辺に最小0.04mのクリアランス。看板/POPの本体外突出は別装飾扱い（既存MVP外周0.10m制約）。影は別パス（外周0.15mまで）。
- マルチ区画を切る場合は境界にギャップや二重支柱を作らない。全体1枚の**統一2Dソース**と内部セグメントを持たせ、各セグメントの当たり判定は全体footprintを参照する。
- 1536×1024等の**原画ピクセルサイズはworld寸法の根拠ではない**。ゲームで映る最終サイズはsource×0.5×zoomが基本。512px/256pxはLODであり設備のランクではない。

## 5. 原画・トリミング・影・透過

- 原画は最初に生成したPNG（または編集可能なSVG/多層画像）を**無変更で保管**し、背景処理・色補正・切り抜きは\`sprite_*\`として派生物を作る。編集・縮小が原画を上書きすることを禁止。
- 透過素材のRGBAが本物か確認する。**RGBの市松模様や黒いスタジオ背景が焼き込まれた画像を「透明」と誤認しない**。alpha=0の四隅だけの確認は不十分。
- alpha \`>=1, >=8, >=128\`でbboxを測り、各辺の最低8 source pxの実物余白とフリンジを判定。低alphaの色付きハロー/反射漏れ/隣接スプライトの異常は独立Visual QA。必要ならpremultiplied alphaの正しい扱いを検証。
- 同一方向のbody、shadow、front/back、glass、商品slotには**同一キャンバス・crop rectangle・anchor**を用いる。anchorは world(0,0,0)基準で数値化し、画像の見かけ中心で推定しない。
- 高い商品やガラスで隠れる部分、客が手前/奥を通る場合は、必要に応じて**背面/商品/前面ガラス/前面遮蔽**へ分割。分割できない1枚絵はレビュー用途に留める。
- 照明・接地影は昼/夜のゲーム側照明と二重にならないよう、別レイヤーまたは合成規則を設定する。

## 6. 生成・編集・合格順

1. **Reference Gate:** 日本式什器写真とユーザーモックアップを比較し、屋根/トレー/ガラス/商品向きと提示した用途の一致を判定。型式の確認が取れるまで量産しない。
2. **Geometry Gate:** 原画のEMPTYまたは商品固定前の構造図で、実寸、2:1軸、各部の位置、r0、world接地を検査。
3. **Stock & Layer Gate:** 商品一体画像の\`FULL\`を生成しても、売れた/補充した際に在庫見た目が一致する仕組みがなければ採用不可。細則は [2D_ASSET_RUNTIME_AND_EQUIPMENT_V1](2D_ASSET_RUNTIME_AND_EQUIPMENT_V1.md)。
4. **Visual Gate:** 画風/包装/濃度/透過/影/値札/ズーム0.5,1,2と背景合成を目視。
5. **Game Gate:** Godot同一レイアウト・同一seed・同一zoomで床/壁/客/ガラス/商品を重ね、移動/回転/売買/保存復元を検証。**スクリーンショットと測定値をIssue添付**。
6. **Approval Gate:** 独立QAとユーザー承認が揃うまでは\`runtime_approved:false\`。開発用overrideで見えたことは正式合格にならない。

## 7. 実装者へのハンドオフ

候補ごとに\`source_original\`、\`game_512\`、\`game_256\`、\`manifest\`、\`QA\`、\`sha256\`、\`actual_subject\`、\`asset_class\`、\`approval\`をそろえる。既存の\`docs/schemas/visual_manifest.schema.json\`は**runtime向け**のため、候補は別の\`docs/schemas/asset_candidate.schema.json\`を使用。見た目が良い生成物も**対象品種の一致・角度・透過・実寸・商品状態の完全検査**が済むまでレビュー専用。
