# 店舗外一体型2D背景・画像生成/GitHub納品パイプライン 詳細仕様 v1.0

更新: 2026-10-29 / 状態: 設計契約（実画面最終QA未実施） / 関連: Issue #102/#123/#157/#163、PR #164。

## 1. 店舗外アート：タイルごとの画像生成をやめる

- **店外の背景・植栽群・生垣・並木・街路・道路縁・街灯群は、原則「連続する2Dコンポジット」単位で制作**。1タイルごとの反復画像生成を禁止。直方体や箱を積んだ「Minecraft風」の外観を避ける。
- 一体化する単位は、背景の長い帯・街路樹＋花壇＋ベンチの自然なシーン群・駐車場＋歩道・建物背後の緑地など。**1つにすることでパース/スケール/縁の連続性が良くなるもの**を優先する。建物の前面、左右・背後の街路、独立する標識や車、前後遮蔽や昼夜で別表示が必要な物は独立レイヤーにする。
- **外観には什器のタイル占有を要求しない**。描画アセットのanchorは世界座標の壁線/角/歩道線に結び、連続位置\`x,y,z\`(m)を許可。描画で床タイル境界を見せず、描画アセットが占有/販売アクセス/通行ルールを変更しない。
- 駐車スペース、歩行可能領域、車止め、看板の論理判定が必要になったら別\`collision/decor\`データに明記する。画像alphaで勝手に障害物を増やさない。
- 小さい画像を大量複製して長さを稼ぐのは禁止。形状の継ぎ目が見える場合は**長いマスター画像を再生成または背景レイヤーごと継ぎ足し**、オブジェクトごとの幅倍率をランダム変更しない。

## 2. 壁の上部に植栽を合わせて隙間ができる問題

**誤り**: 植栽画像の底/背景を「壁の最上辺のスクリーンY」に合わせると、壁面の背後に見えるべき幹や低木が宙に浮き、壁の背後の地面に大きな空白ができる。

**正しい実装（壁を物理座標基準に固定）**:

1. 外壁edgeの始点・終点を\`world_start/world_end\`（m）で取得し、対象壁の高さ\`wall_height_m\`はゲーム既存の値（\`IsoProjection.WALL_HEIGHT_M=2.6\`）を使う。
2. 植栽合成画像に少なくとも\`ground_anchor_world\`、\`height_world\`、\`bounds_world\`、\`wall_segment_id\`、\`occlusion_mode\`を設定。**植栽の根元は壁の足元の地盤に設置**。スクリーン画像上端・壁の頂点は位置合わせに使わない。
3. 壁の向こう側で植栽が壁に隠れてよいことを前提に、**根元/幹の下部は壁の背面に隠す**。高木の枝・葉は壁の上に伸び、上部だけが見える。植物の\`world_z\`を壁上端に合わせて上げない。
4. 壁の**背面レイヤー**に植栽・遠景・背景帯、次に外壁の不透明部分、次に店舗の窓/手前歩道/街灯を描く。壁を跨ぐ高木は\`behind_wall\` / \`above_wall_visible\`の2マスク、または同等のシルエットクリップで表現する。
5. **右端の長さ不足**を防ぐには、画像の描画幅ではなく**壁のworld始点/終点をスクリーン投影**してカバー率を測る。合成植栽の左右端は壁両端をそれぞれ0.10m以上カバー（当初の提案値、画角変化の実画面で最終調整）。足りなければアセット自体を延長再作画し、非等方拡縮で無理に延ばさない。
6. 壁の折れ点で背景帯を連結するときは**同じ色調・カメラ投影・光源**を使用。継ぎ目の二重木・不自然な連続反復を手動/機械両方で検査。

**視覚テスト**: 対象壁の左端・中央・右端、昼/夜、zoom0.5/1/2、建物の前景/背面を撮影し、植物の浮遊・壁上端の水平帯状の穴・右側切れ・壁の貫通・客/車と背景の前後逆転がないこと。壁の塗り自体は従来仕様で変更しない。

## 3. 外観の層・昼夜・サイズ・演出

- \`background_far\`: 遠方の街並み・空・樹冠帯（特定タイル占有なし）。
- \`behind_store_wall\`: 店舗裏の花壇/高木/生垣。壁より背後・地面に接地。
- \`store_architecture\`: 店舗外壁、軒、ドア、ガラス窓、サイン、壁の開口。
- \`street_ground\`: 駐車場、アスファルト、歩道、車止めと白線。店舗の地面論理と分離したタイル非依存テクスチャ帯。
- \`street_props\`: 自販機、看板、駐輪場、ベンチ、ポスト、街灯、植木鉢、車、ゴミ箱。これは必要に応じて独立した2Dプロップ。
- \`street_foreground\`: 手前側の花、低木、車体の前景面、街灯の部分遮蔽。
- \`lighting_overlays\`: 店内から漏れる光、外灯、夜間反射。昼夜やイベントでのON/OFFは描画だけが担当し、Domainの売上計算へ影響させない。

**スケール**: 店内と同じ\`iso2x_v1\`でanchorを持つ独立物は同じ世界→スクリーン換算を使用。世界背景のパララックスはMVPで独自実装せず**固定カメラの縮尺**に従う。長い背景帯の連続模様は1:1タイル上に小片の周期模様を作らず、**壁長さや道路長さの実寸から生成**。

**明るさ**: 元アートのシーン内光源方向を一定にする。夜間はゲーム既存の照明・modulateで調整し、画像の暗いスタジオ背景を使用しない。立体感を出すための焼き込み影は本体下だけ。長い影や外灯のスポットは照明レイヤーに分離し、昼/夜で二重投影しない。

**権利/内容**: 日本のコンビニらしい店構えをモデルにするが、実在ブランドロゴ、看板商標、ゲームで使えない第三者撮影画像をそのまま流用しない。商品名・値札・価格は架空/Domain基準。

## 4. ChatGPT生成 → Codex調整 → 独立QA の境界

| 担当 | 主な仕事 | **してはいけないこと** |
|---|---|---|
| アート/ChatGPT画像生成 | 什器型式、商品、画風、棚本体＋陳列の高品質原画を生成。必ず1種類/1設備IDに分類し、原画像を保管 | 指定が「おでん」なのに「パン」になった画像をおでんとして命名する |
| Projection/Geometryサブエージェント | r0～r3、world寸法、ground pivot、footprint、客側の向き、レイヤー分割、Godotオーバーレイ | X/Yだけ伸縮、単純ミラー、1×2へ大型設備を強制縮小 |
| Visual/Reference QAサブエージェント | 日本の実店舗写真との比較、roof/棚板判定、透明ハロー、画風/商品ラベル、ズーム品質 | 本体を作ったエージェントの「自称PASS」をそのまま承認する |
| Runtime/Gameplayサブエージェント | Domain stock同期、LODと設備grade分離、4方向、セーブ互換、既存fallback | JPEG/PNGピクセルサイズで容量/売上/電力を変える |
| Artifact/Gitサブエージェント | PNG/WebP/manifest/SHA/完全ZIPの実ファイルをコミットしてGitHub再取得/照合 | Base64転送テキストやスクリプトだけで「画像登録済み」と報告 |

**継続運用**: 同一Agentを1回の画像生成で完了扱いにせず、Issueを作業キューにして\`reference review → generate → geometry QA → in-game test → fix → audit → next\`の反復に投入。異なる担当は独立worktree/ブランチで作業し、同一画像やmanifestを無断で同時編集しない。blockedの場合は原因を記録して**非競合の別作業**を選ぶ。承認や破壊的変更はユーザーの指示なしに進めない。

## 5. ファイル配置・コンテンツ識別・ZIP契約

\`\`\`text
assets/source/chatgpt_2d_interior/<asset_id>/
    source_original.png            # 生成された無加工原画、上書き禁止
    source_original.svg            # SVGで制作した場合、代替可
    sprite_fullres.png             # 透過処理済み候補、必要なら
    source_fullres.webp            # 原寸の最適化版、必要なら
    game_512.png
    game_256.png
    manifest.json                 # 詳細な候補状態/sha/寸法/品質
    README.md
    qa/                           # 角度比較/画像alpha/スクリーンショット
assets/source/chatgpt_2d_interior/_bundles/full/<asset_id>_full.zip
assets/source/chatgpt_2d_interior/_bundles/<asset_id>_compact.zip
assets/review/imagegen_candidates/<date>/...  # 不採用・角度不一致の元画像も保管
\`\`\`

- **Source**: 原画のSHA-256とbyte数を保存。無加工ソースから派生物を作り、原画は上書きしない。
- **Bundle full**: 原寸source、利用する派生版、manifest、README、QA証跡、ライセンス情報を必須。元ファイルとZIP展開後のSHA-256を完全一致させる。ZIPは圧縮形式自由だが再現可能なファイル名・重複なし・パストラバーサルなし。
- **Bundle compact**: 表示用512/256とmanifest/README、必要ならWebP。**原寸PNGが入っていないことを明記**。compactしかGitHubにない場合、full登録を完了扱いにしない。
- **GitHub登録**: Draft PR上のblobが**実PNG/WebP/ZIP**であること。GitHub APIで存在確認し、可能な範囲でbytesとGit blob SHAを照合。ローカルSHA-256とGit blob SHAは別アルゴリズムなので比較しない。大容量時はZIPを分割したりテキストだけ登録して「登録済み」にすることを禁止。
- **GitHubのAPI/UIの制限**: 巨大なbase64応答が空でもblob SHAは確認できる。内容の詳細検証にはraw/ダウンロードしたバイナリを実際に読める環境で取得し\`sha256sum\`/ZIP展開検査を行う。空のbase64応答だけで「画像破損」と断定しない。
- **Manifest**: アート候補用\`docs/schemas/asset_candidate.schema.json\`を使い、\`github_uploaded\`は物理的にアップロード成功後のみtrue。レビュー候補が\`runtime_approved:true\`になってはいけない。
- **導入**: Godotの\`assets/generated/fixtures/<id>/<id>.visual.json\`はruntime用。候補パスを直接コピーしても承認にはならない。必要な4方向・在庫レイヤー・サイズ・アクセス・fallbackを満たした**別PR**で結線する。
- ファイルが大きい場合はGit LFS/リリース添付/アセットパック分離も検討できるが、**ユーザーの運用承認と再現性検証なしに切替しない**。既存ZIPと原画の削除禁止。

## 6. 品質ゲートと終了条件

| Gate | 証拠 | FAILの例 |
|---|---|---|
| G0 種別・参照 | 実売場写真とユーザーモックアップのOK/NG図 | 菓子棚に厚い屋根、別の商品分類 |
| G1 形状・投影 | world 1m軸の数値、r0～r3のfloor overlay、複数ズームの同画面 | 画像の長辺傾斜だけが合っているように見える |
| G2 alpha/描画 | alpha1/8/128 bbox、陰影・ガラス・遮蔽比較 | 背景に黒いハロー/端への接触 |
| G3 Domain整合 | EMPTY/LOW/MEDIUM/FULLの在庫操作、SKU表示 | 売切れでも満棚、セーブ後誤表示 |
| G4 サイズ/性能 | 論理footprint、通路、LODと設備gradeの独立試験 | 256px画像を低容量設備と誤認 |
| G5 納品 | SHA256、Git blob、ZIPテスト、PR/Issueリンク | 完全ZIP欠落、manifestのみ登録 |
| G6 実機最終 | Godot screenshot/操作/ユーザー承認 | 画像が入っただけ、未確認でmainマージ |

- G0～G6を満たすまで**Draft、\`runtime_approved:false\`**を維持。プレビュー画像、Codex計測やチェックリストだけでCloseしない。
- 実画面の目標条件: 1280×720と1920×1080、zoom0.5/1/2、昼/夜、壁の左・中央・右、隣接・客前後、設置/回転/売り切れ/補充を固定seedで検証。
- 新アセット品質の根拠は**GitHub上の実PNGへのリンク**を使用。ChatGPT画面に類似画像を検索表示しても登録ファイルのプレビューとして提示しない。
