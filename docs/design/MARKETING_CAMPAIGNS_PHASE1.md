## 2. 移行方針（A と B の比較）

| 観点 | A: 5段階ティアを媒体プランに置換 | B: ティアを「一般認知」として残し、媒体を上限付きの別効果として追加（**推奨**） |
|---|---|---|
| 既存コード | `SET_NEXT_DAY_AD`、`advertising` セーブ、`test_advertising.gd`、UI を全面改修 | 既存コマンド・セーブ項目を維持。ティアは「一般認知」媒体として1行に位置付け |
| 二重計上 | 起きにくい | 起きうる → **共通の上限**と「ティアは1つの媒体」扱いで防ぐ |
| 既存テスト | 大半が書き換え | 既存は「媒体ゼロ時に従来どおり」の回帰テストとして残せる |
| 段階実装 | 一度に大きい | PR 単位で分けやすい |
| 利用者の混乱 | 旧ティアが消える | 旧ティアは残るが、予約画面で「一般認知（従来どおり）」と明示 |
| 将来（#129 ライバル） | 扱いは同じ | 同じ（ライバル効果は需要側の別乗数） |

### 2.1 推奨: B（ただし次の2条件付き）
1. ティアの乗数は媒体効果と**同じ加算プール**に入れ、単独では掛けない（現行の `ad_multiplier` 乗算を廃止）。
2. 媒体の効果は「**一般認知の上限**」を共有し、全体の加算は +60% で頭打ち（§3.4）。

### 2.2 合成式（上限と逓減つき）

日 d の来店希望（潜在来店）:

```
L_media(d) = Σ_c  Lmax_c × (1 − exp(−A_c(d) / S_c)) × share_c(time_band)
L_general(d) = arrival_multiplier(tier_d) − 1          # #18 ティア（0〜0.40）
L_mkt(d)   = min(L_CAP, L_general(d) + L_media(d))     # L_CAP = 0.60

potential(step) = base × hour_w × reputation × assortment
                  × event_traffic                       # #31（0.70〜1.40、既存）
                  × (1 + L_mkt(d))
                  × rival_share                         # #129（後続。Phase 1 では 1.0）
p = clamp(potential / STEPS_PER_DAY, 0, 1)
```

- `A_c(d)` は媒体ごとの**効果ストック**（後述 §3.2）。過去の出稿が残効として残り、同じ出稿の繰り返しでは逓減する。
- `share_c` は時間帯指定（ラジオの通勤帯など）の対象割合。全日指定は 1。
- カテゴリ効果（ネット広告の対象カテゴリ）は別乗数 `M_cat(d) = min(1.30, 1 + Σ cat_lift_c)`。`category_weight` 側で #31 のカテゴリ乗数と掛け、**カテゴリ重みの最終値は 2.5 で打ち切る**。
- 全体の需要乗数（マーケ × イベント）は **2.0 で打ち切る**（`traffic_total_cap`）。

ねらい: 広告に上限があるため、最大は `1.60 × 1.40 = 2.24` 倍までで、2.0 で止まる。無制限の掛け算は起きない。

## 3. 4 媒体の仕様（仮説）

### 3.1 共通パラメータ

| 記号 | 意味 | 値（仮） |
|---|---|---|
| `g` | 1来店あたり粗利 | 84 円（§1.1、残高テストで実測に置換） |
| `V0` | 基本潜在来店 | 50 人/日 |
| `r_c` | 残存率（翌日へ持ち越す効果の割合） | 媒体別（表） |
| `S_c` | 飽和点（効果ストックがこの値の約63%で頭打ちに向かう） | 媒体別 |
| `Lmax_c` | 最大リフト（来店増の上限率） | 媒体別 |

### 3.2 効果ストックの更新（ゲーム日の境界、課金の後）

```
A_c(d) = r_c × A_c(d−1) + gain_c(d)
gain_c(d) = 出稿1回の点数（媒体別）        （新聞・ラジオ・テレビ: 1点/掲載）
         = 1.5 × (1 − exp(−spend_c(d) / 1000))  （ネット: 日予算 spend）
```

- 掲載がない日は `gain = 0` で、A は `r` の割合だけ減衰する（ramp / peak / decay はこの形で出る）。
- 掲載ゼロでも効果は残るが、**残存率を超えて増えない**（逓減）。

### 3.3 媒体パラメータ表（すべて仮説）

| 項目 | 新聞 `newspaper` | ラジオ `radio` | ネット `web_ads` | テレビ `television` |
|---|---|---|---|---|
| 制作費（一回・予約時） | 1,000 円 | 2,000 円 | 0 円 | 30,000 円 |
| 1掲載・1日あたり費用 | 500 円/掲載 | 600 円/日 | 日予算（300〜3,000 円） | 8,000 円/放映 |
| 予約リードタイム | 1 ゲーム日 | 2 ゲーム日 | 1 ゲーム日 | 5 ゲーム日 |
| 掲載期間 | 1〜3 日 | 2〜5 日 | 1〜7 日 | 3〜5 放映 |
| `gain` / 掲載 | 1.0 点 | 1.0 点 | 1.5×(1−e^{−spend/1000}) | 1.0 点 |
| 残存率 `r` | 0.2 | 0.5 | 0.4 | 0.6 |
| 飽和 `S` | 1.0 | 1.0 | 1.5 | 2.0 |
| 最大リフト `Lmax` | 0.15 | 0.50（時間帯内のみ） | 0.25 | 0.60 |
| 効く時間帯 | 全日（朝・昼に相対的に強い仮定） | **通勤帯 7–9 時・17–19 時のみ** | 指定可（全日 or 1帯） | 全日 |
| 効く客層／カテゴリ | 全体。`rice_ball` と `bread` の重み ×1.10 | 全体。`drink` と `bread` の重み ×1.10 | 指定 1カテゴリの重み ×最大 1.30 | 全体。評判 +1/放映日（上限: 1日 +1、累計 +3） |
| 目的（objective）との相性 | 近隣の固定客 | 通勤・朝夕の購入 | 在庫過多の解消・特定カテゴリ | 認知・新店 |

- ラジオの通勤帯割合: 時間帯の重み（`normalized_hour_weights`）で計算すると、7–9 時と 17–19 時で**来店重みの約32%**。`share = 0.32`。
- テレビの評判効果は `reputation` の日次変動上限（`max_daily_change = 3`、既存）の範囲内に収める。

### 3.4 1日の効果（ramp / peak / decay の例）

前提: 来店 50 人、g = 84 円、基本粗利 4,200 円/日。「回収率」= 期間中の粗利増 ÷ 広告費（**in-run ROAS**）。

| 例 | 費用合計 | 日別リフト（1日目→） | 粗利増（合計） | 回収率（推定） |
|---|---|---|---|---|
| 新聞 1回 | 500 + 制作 1,000 | +9.5% | 約 400 | 約 0.27（制作費込み）/ 0.80（掲載費のみ） |
| 新聞 3回連続 | 1,500 + 1,000 | +9.5 → +10.5 → +10.6% | 約 1,290 | 約 0.52 |
| ラジオ 3日 | 1,800 + 1,000 | 通勤帯 +31.6 → +38.8 → +41.3%（share 0.32 込み実効 +10.1 → +12.4 → +13.2%） | 約 1,500 | 約 0.54 |
| ネット 1,000円/日 × 3日 | 3,000（制作 0） | +11.7 → +14.7 → +15.7% | 約 1,770 | 約 0.59 |
| テレビ 3放映（既定案） | 30,000 + 24,000 = 54,000 | +23.6 → +33.0 → +37.5% | 約 3,950 | **約 0.07** |

読み取り:
- 新聞・ラジオ・ネットは「**小さく何度も**」で回収率 0.5〜0.6 前後。残効と評判を加えると 1.0 近くに届く設計余地がある。
- テレビは既定案では**回収できない**（0.07）。実際の地域テレビ広告費に寄せた数字であり、この店の売上規模（1日約 4,000 円の粗利）では回収に数か月かかる。これは「テレビは高い」を正確に表すが、ゲームとして遊べるかは別問題。**§6 の決定事項 2 で扱う**。
- 広告費の現実味: 1回 500 円の新聞、1日 1,000 円のネットは、現行ティア（1,000 円/日）と同じ桁で、「国全体のテレビを数千円」のような不自然さは避けている。

### 3.5 ROI 目標帯（残高テストの合否基準・仮）

| 媒体 | 目標 in-run 回収率 | 判定 |
|---|---|---|
| 新聞 | 0.6〜1.0 | 0.4 未満は「ほぼ無意味」 |
| ラジオ | 0.5〜0.9 | 時間帯を外すと 0.2 以下になることを確認 |
| ネット | 0.5〜1.0 | 過剰出稿で 0.3 以下に落ちる（逓減）ことを確認 |
| テレビ | 0.2〜0.6（残効・評判込み） | 0.1 未満は調整対象（決定事項 2） |

- 「どれか1つが常に最適」にならないよう、新聞は小規模・短期、テレビは遅い・長期、ラジオは時間帯、ネットはカテゴリ向き、と**勝ち筋を分けて**テストする。

## 4. キャンペーンのライフサイクルとデータモデル

### 4.1 状態遷移

```
DRAFT（画面上の見積もり）
  → BOOKED（予約。制作費を即時請求。start_day = 予約日 + リードタイム）
      → AIRING（掲載日の開始で日次請求。効果が効き始める）
          → ENDED（end_day 経過）
  → CANCELLED（開始前のみ。制作費は返金しない・仮）
  AIRING 中に資金不足 → UNPAID_DAY（その日は効果ゼロ、警告。以降の日は請求を再試行）
```

### 4.2 データ項目（`GameState.campaigns: Array[Dictionary]`）

| 項目 | 型 | 例 |
|---|---|---|
| `campaign_id` | string | `cmp_00001`（連番。`next_campaign_seq` で採番） |
| `medium` | string | `newspaper` / `radio` / `web_ads` / `television` / `general_tier` |
| `objective` | string | `new_customers` / `regulars` / `category_push` / `awareness` |
| `target` | dict | `{"category": "bread" or null, "time_band": "all" / "commute" / "morning" / "lunch" / "evening"}` |
| `daily_budget_yen` | int | 500（新聞1掲載）/ 1,000（ネット日予算） |
| `setup_cost_yen` | int | 1,000 |
| `booked_day` / `start_day` / `end_day` | int | 4 / 6 / 8 |
| `status` | string | `booked` / `airing` / `ended` / `cancelled` |
| `spent_yen` | int | 累計の掲載費（制作費を含む） |
| `billed_days` | array[int] | `[6, 7]`（請求済みの日。二重防止の補助） |
| `effect_stock` | float | `A_c`（§3.2） |
| `applied_event_ids` | array[string] | `["cmp_00001:setup", "6:MEDIA:cmp_00001", …]` |

### 4.3 台帳の event_id（冪等性）

| 種類 | event_id | event_type | 集計先 |
|---|---|---|---|
| 制作費（予約時） | `cmp:<id>:setup` | `AD_SETUP` | `advertising_yen` |
| 掲載費（日次） | `<day>:MEDIA:<id>` | `AD_MEDIA` | `advertising_yen` |
| 一般認知ティア（従来） | `<day>:AD` | `AD`（従来） | `advertising_yen` |

- `BusinessService.KINDS` の拡張で `day_charged` の判定を媒体分にも広げ、**ゲーム日の請求が媒体を含めて一度だけ**になるようにする。
- 予約・取消のコマンドは `applied_command_ids` で二重適用を防ぐ。

### 4.4 日次請求と効果の順序（日付境界・固定順）

1. 前日の日次締め（`DailyReport`）。
2. 当日の請求: 一般認知ティア → 掲載中の媒体 → 固定費 → 電気（既存順を維持）。資金不足の媒体は `UNPAID_DAY`（効果ゼロ・負債なし）。
3. 効果ストック `A_c(d)` の更新（請求が成功した媒体のみ `gain` を入れる）。
4. #31 のイベント抽選（`events` RNG。既存どおり OPEN の最初のステップ）。
5. 以後の来店抽選で `L_mkt` と `M_cat` を使う。

- 一時停止・4倍速・SAVE/LOAD で境界を跨いでも、手順 2 は `has_event` で二重請求しない。
- 手順 3 は「同じ日に一度だけ」（`billed_days` と `last_effect_day` の両方で判定）。

### 4.5 セーブ移行（SCHEMA_VERSION 2 → 3）

- 追加: `"campaigns": []`、`"marketing": {"next_campaign_seq": 1}`。
- 2 → 3 の読み込みは空配列で補う（#128 の 1 → 2 と同じ方式）。
- 既存の `advertising` ブロックは変更しない（一般認知ティアの互換）。
- `save_game.gd` の許可イベント一覧（`AD`、`AD_SETUP`、`AD_MEDIA` を追加）と `ledger_summary.gd`（`advertising_yen` の集計先）を同時更新。
- `docs/schemas/savegame.schema.json` も更新。

## 5. 日次イベント（#31）・ライバル（#129）との関係

### 5.1 適用順（来店計算）

| 順 | 乗数 | 範囲 | 上限 |
|---|---|---|---|
| 1 | 基本 × 時間帯 × 評判 × 品揃え（既存） | — | — |
| 2 | 日次イベント `traffic`（#31） | 0.70–1.40 | イベント単体 |
| 3 | 広告・販促 `1 + L_mkt` | 1.00–1.60 | `L_CAP = 0.60` |
| 4 | ライバル `rival_share`（#129、後続） | 0.6–1.0（案） | — |
| 5 | 全体の需要乗数 | 0–2.0 | `traffic_total_cap = 2.0` |

- カテゴリ側: イベントの `category_weight_multipliers`（1.0–1.80）× 広告の `M_cat`（最大 1.30）。最終重みは **2.5 で打ち切る**。
- 効果の**キャップ優先順位**: 最終的に打ち切るのは「広告」側（イベントを優先）。イベントは時間窓が明確で、ユーザーに見えているため。

### 5.2 同時に複数媒体を出す場合

- 同じ対象（同じ時間帯・同じカテゴリ）の重複は、`Σ` で加算した上で逓減（`1 − exp`）が効く。
- 媒体数の上限は設けない（逓減と `L_CAP` で十分）。ただし UI では同時実施 4 件まで（表示の複雑化を防ぐ）。

### 5.3 #129 への接続（後続）

- `rival_share` は、潜在来店から直接引く（来店を奪う）。広告と競合は独立に掛け、どちらも単独で 0 にならない下限を置く（0.6）。
- 競争イベントは `GameplayEventDirector` と同じ形（重み付きの 1 日 1 回抽選）で追加し、広告と同じ乗数の列に入る。

## 6. ユーザーが決める事項（レビュー用）

1. **既存ティアの扱い**: 推奨 B（一般認知として残し、加算プールに統合）。旧ティアの乗数は §2.3 の方向で再調整。
2. **テレビのコスト水準**: 現実寄りの既定（回収率 約 0.07、評判・長期の投資）か、ゲーム寄りに下げる（制作費 10,000 円・放映 3,000 円程度で回収率 約 0.2〜0.3）か。遊びやすさと現実味のどちらを優先するか。
3. **予約後の取消・返金**: 制作費は返金しない（推奨）／開始前の取消で 50% 返金。
4. **上限値**: 全体の広告加算の上限 `L_CAP = +60%`、需要乗数の上限 `2.0`、同時実施 4 件。
5. **バスケット（点数）への効果**: Phase 1 では **しない**（来店数とカテゴリ重みのみ）。広告で一度の買い物点数が増えるのは Phase 2 以降で検討。

## 7. UI（経営タブ内「広告・販促」画面）

### 7.1 画面構成

| 領域 | 内容 |
|---|---|
| 上段: 媒体カード 4 枚 | 媒体名、一言の得意分野、制作費、1掲載（日）あたり費用、リードタイム、期間の目安 |
| 中段: 設定フォーム | 目的（4 種）、対象（カテゴリ / 時間帯）、日予算または掲載回数、開始日（リードタイム後が最短）、期間 |
| 予報（推定） | 「予測（推定）」と明示した来店増の見込み、費用、回収率の見込み。**根拠の数字（基本来店 50 人、g）を併記** |
| 進行中・予約済み | 一覧（状態、残日数、累計費用、現在の効果ストック） |
| 結果（日別） | 掛けた費用、推定の増分来店、推定の粗利増、差引（純効果）、CPA（来店1人あたりの費用）、ROAS（回収率）。**すべて「推定」ラベル** |
| 影響要因 | 同時に起きたイベント、欠品、営業時間外、容量超過（入店できなかった来店）を注記 |

### 7.2 通知の抑制

- 予約確定・開始・終了の 3 回だけトースト。毎日の掲載は通知しない（日次レポートに集約）。
- 資金不足の掲載は 1 回だけ警告。

### 7.3 「客が急に画面を埋めない」ための仕様（ユーザーの要望）

- 広告は**来店希望の確率**を上げるだけで、客を直接生成しない（既存の `arrivals` 抽選のまま）。
- 増えた来店希望は `max_active_customers = 30` の容量で制限され、超えた分は `lost`（入れない）として数えられる。
- 効果は **ramp（掲載の翌日から効く）** のため、初日に一気に増えない。残効は日単位で減衰する。
- 画面には「来店希望」「入店」「入店できず」を分けて表示し、混雑の原因を見せる。
- 広告による追加の客はスポーン数に直接乗せず、既存の到着キュー経由とする（描画負荷と見た目の急変を防ぐ）。
