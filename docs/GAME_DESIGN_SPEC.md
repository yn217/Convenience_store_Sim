# Convenience_store_Sim — 詳細ゲーム仕様書

> Status: Draft v0.2 / 2026-10-22 / 方針: リアル寄り2.5Dアイソメトリック
> 本仕様はMVPの実装契約。未決定事項は「暫定」と明記し、実装中に暗黙の仕様変更をしない。

## 0. 目的・体験

日本のコンビニエンスストアを舞台に、プレイヤーが売場の設備をタイル単位で配置し、商品を仕入れ・陳列し、来店客の動き、売上、粗利益、広告、廃棄を管理するシングルプレイヤー経営シミュレーションゲーム。

**コアループ**: 店舗配置 → 商品仕入れ → 補充/値付け → 営業開始 → 客が商品を選択・レジ会計 → 日次決算 → 改善。

**MVP成功条件**: 空店舗から棚・冷蔵ケース・レジを置き、8カテゴリの商品を仕入れ、客が棚に接近・買物・会計し、売上/在庫/損益が矛盾せず変化し、保存/再開できる。

## 1. 決定事項と非対象

- **描画方式**: 2.5Dアイソメトリック。3Dモデルを制作時に正投影レンダリングし、ゲーム内は2Dスプライト。リアル寄り、清潔感のある日本のコンビニ表現。
- **エンジン**: Godot 4.x / GDScript（初期採用）。シミュレーションの状態・規則は描画層と分離。
- **初期対象**: PC、マウス＋キーボード、ローカルセーブ、単店舗、オフライン。
- **初期店舗**: 16×12タイル（暫定）。論理1タイル=約1m×1m（暫定）。ズーム可・画面パン可・実行時カメラ回転なし。
- **初期カテゴリ**: おにぎり、おでん、カップラーメン、パン、飲料、おかし、デザート、アイス。各カテゴリ最低3SKUをサンプル投入。
- **非対象（MVP後）**: 複数店舗、マルチプレイ、配送車の実経路、高度な店員シフト、実在ブランド、ネット広告API、本格的な店舗建設/改築、可動3Dカメラ、現金流量の複雑な会計制度。
- **用語**: 什器=販売用設備、SKU=個別商品種類、バックヤード在庫=未陳列の保有数量、棚在庫=什器に陳列中の数量、粗利=売上−売上原価。

## 2. 画面・操作仕様

### 2.1 画面構成
1. **中央店舗ビュー**: 床/壁/入口/什器/陳列商品/客/店員（MVPでは店員の会計アニメ省略可能）を描画。オブジェクト選択枠、接近不可の警告、設置プレビュー。
2. **左：建設・配置パレット**: 「構造」「棚」「冷蔵/冷凍」「ホットフード」「レジ」「装飾」。サムネイル、占有寸法、価格で選択・検索。
3. **右：選択インスペクタ**: 名前、占有寸法、向き、購入/撤去価格、売場種別、棚容量、在庫/売上、価格設定、補充。
4. **上部HUD**: 所持現金、ゲーム内日時・速度、一日売上、当日推定粗利、来店数、広告費、低在庫警告。
5. **下部/タブ**: 仕入、広告、損益/日次レポート、商品マスタ、設定、セーブ。

### 2.2 操作
- 左クリック: タイル/什器の選択。配置中は設置確定。
- 左ドラッグ: 配置中プレビュー移動。配置済みの移動は明示的「移動」操作またはドラッグ開始ハンドルを使い、誤移動防止。
- R: 配置プレビュー/移動中の什器を90°回転（4方向）。Esc/右クリック: キャンセル。
- マウスホイール: 中心点基準ズーム（例0.5〜2.0倍、暫定）。中ドラッグ/Space+左ドラッグ: パン。
- 速度: 一時停止、1×、2×、4×。設置中の時間停止は設定で切替可能（MVPは自動停止）。
- Delete: 選択中の什器を撤去（確認あり）。Ctrl+Z/Ctrl+Y: **配置編集**のUndo/Redo（売買・会計など時間進行済みイベントには適用しない）。
- 操作不能時には理由を可視化。重複/アクセス不可/資金不足/出入口封鎖を区別。

### 2.3 表示モード
- 通常: リアル寄り2.5D描画。床グリッドは原則非表示。
- 配置: 床グリッド・占有・設置可(緑)/不可(赤)/警告(黄)・アクセス方向矢印・経路の到達性を表示。**色だけに頼らず記号/文言でも表示**。
- 情報: 通行量、売上ヒートマップ、低在庫、設備到達不能を表示（高度なヒートマップは拡張）。背の高い什器が隠す対象には透過/アウトライン選択補助。

## 3. 店舗タイルと2.5D投影

### 3.1 論理モデル
- 店舗は直交配列 tile[y][x]。座標系: xは東、yは南。原点(0,0)は論理店舗の北西。
- 1タイルの基本属性: floor_type, zone, buildable, walkable_base, structural_block, occupant_instance_id (nullable)。
- **派生値**として移動可否・アクセス可否を再計算。重複したwalkable状態の別保存は避ける。
- 固定設備（壁、入口、構造柱）と配置什器を別レイヤーにする。
- サンプル店舗: 16列×12行、入口2タイル、レジは初期配置しない（ユーザーが設置）。
- 必須入口は建物の固定構造。入口の通行口タイルを設置物で塞げない。

### 3.2 投影と並び順
- 表示グリッドの1タイルの菱形: 幅128px、高さ64px（基準ズームでの暫定値）。位置は
  screen_x = origin_x + (x−y)×64,
  screen_y = origin_y + (x+y)×32 − elevation_px。
- ゲーム座標と描画座標は独立管理。マウス位置は逆変換し、選択対象はタイル/不透明ピクセル/選択枠を適切に判定。
- スプライトの基準点は接地アンカー。タイル原点、論理占有ポリゴン、クリック判定をメタデータで関連付ける。
- 奥行き順は**足元/接地位置基準**で描画ソートし、巨大什器は占有領域の手前端を適切に扱う。壁・什器・客の前後表示を実店舗サンプルで検証。
- 床・什器・動的キャラ・警告UIはレンダリング層分離。UIは世界座標の深度ソートに巻き込まれない。

### 3.3 什器占有・向き
- 規格は1×1、1×2、2×2、1×4、2×4など **(w,h)整数タイル**。SKUや商品画像は占有を増やさない。
- 設置はグリッドにスナップ。回転は0/90/180/270の4段階、奇数回転でw/h交換。
- 「front/left/right/back」のアクセス面は什器ローカル方向として定義し、回転とともに座標変換。
- 設置判定: 範囲内、buildable、占有競合なし、必要資金、不可侵エリア非侵入、少なくとも1つの販売アクセス位置への到達可能性、入口→レジの到達可能性。
- **ハードエラー**（確定不可）: 重複、範囲外、建物不可侵箇所、入口封鎖。**レジが設置済みの場合だけ**、入口→有効レジの必須動線の分断もハードエラー。初期状態のレジ0台は合法な建設状態であり、営業開始操作のみ拒否する。
- **警告**（確定可能だが効率悪化）: 売場へのアクセス不足/一部死に棚、通路幅1、混雑見込み。MVPで売場が全くアクセス不可ならハードエラーにしてもよいが、ルールは一貫させる。
- 顧客が通れるタイルと棚に接するタイルは異なる概念。商品棚そのものは不可侵、手前隣接タイルがアクセス位置。
- 経路探索: Godot AStarGrid2D相当。入口からレジ/各什器の到達可能アクセス位置を計算し、構造変更時のみ経路キャッシュを無効化。

### 4.2 共通什器スキーマ
- fixture_type_id, display_name, footprint, allowed_categories, placement_cost, removal_refund, max_capacity, access_sides_local, customer_service_seconds, electricity_cost_per_day, appeal_modifier（いずれも仮値を設定）
- instance_id, fixture_type_id, origin_tile, rotation_quadrants, stock_slots[], enabled, lifetime_sales, occupancy_generation は実店舗側のインスタンスデータ。
- 什器容量と商品スロットの占有関係を定義。1スロット単一SKU、合計qtyは最大容量以下。
- 表示状態: empty / low / medium / full を在庫から計算。スプライト差し替えまたはレイヤー合成。

### 4.3 2.5Dアセットパイプライン
1. Blender Pythonで**規格寸法の什器**をモデリング（棚板、金属枠、扉、照明、影）。複数ケースで形状部品を再利用。
2. カメラは全アセット共通の正投影・固定角度。床菱形2:1の見た目と投影整合を取る。照明、影、露出、ホワイトバランスを統一。
3. 各什器について4方向（0,90,180,270°）の透過PNGまたはWebPを生成。対称アセットの省略は試験後に限定。
4. **接地アンカー、画像のピクセル寸法、占有w/h、描画オフセット、向き、当たり/選択領域**をJSONマニフェストで出力。
5. スプライトをGodotにインポート。グリッド基準位置との画像ズレ、背面透過、前後ソート、拡大縮小時のにじみを目視/自動検証。
6. 元モデル/生成スクリプト/ライセンス/生成パラメータを追跡可能に保管。商品パッケージは架空ブランド（実在商標と混同しない）。
7. 商品の見た目は共通単純形状（おにぎり三角、飲料円柱、カップ麺円錐台、菓子袋など）＋AI生成ラベルで差し替え。ローカル画像生成の結果は必ず人手レビュー。

**重要**: 画像生成AIだけで寸法の正確な棚一式を量産しない。メッシュ/スプライトの幾何形状をプログラムで確保し、AIをラベル・ポスター・装飾に使用。

### 4.4 表示品質
- 基準アート: 高解像度、清潔感、落ち着いた照明、金属/ガラス/プラ素材の差、読みやすい棚配置。
- 視界制御: 高い冷蔵庫が背後の棚/客を隠す場合、選択中の透明化/輪郭表示。商品識別はインスペクタに文字でも表示。
- レベルオブディテール: 遠景=カテゴリ色/商品塊、中景=容器群、近景=ラベル差が分かる。絵柄ではなく表示スケールに基づいて切替。
- スプライト著作権/商標/生成元を記録。第三者ブランドや実店舗ロゴは使用しない。

## 5. 商品・仕入・在庫

### 5.1 商品マスタ
product_id, name, category, purchase_cost, base_sell_price, allowed_fixture_categories, shelf_life_hours (nullable), demand_weight, appeal, visual_id, package_size/slot_units。
- 通貨は円整数。税制度はMVPでは簡略化し、表示価格と売上計算を同じ税込/税別ルールに統一（MVPは**税計算省略、ゲーム内価格で統一**）。
- SKUに複数の補充ロット/賞味期限がある場合はFIFO/FEFO（期限の早い順）を明示して販売/廃棄に使用。

### 5.2 在庫フロー
- 仕入発注 → 仕入費用は発注確定時に現金から減額（暫定） → 納品待ち → バックヤード在庫へ → 什器への補充 → 販売 → 棚在庫減少/会計確定。
- MVPは即時納品か1時間後納品かをUIで固定（**暫定: 即時納品**）。後でリードタイム拡張可能なイベント型。
- 複数箇所在庫の二重計上・負数化・什器容量オーバーを禁止。
- 補充は手動UIを基本。自動補充はMVP後。商品カテゴリーと什器互換性を検証。
- 賞味期限あり商品はロット別保有数量/期限。経過時に棚/バックヤードの残数を廃棄し、販売不可にする。
- 保存/ロード後も発注、棚、バックヤード、ロット、価格が保たれること。

### 5.3 初期例（バランス仮値）
- おにぎり: 原価100円、販売150円、賞味期限24h
- カップ麺: 原価130円、販売210円、長期保存
- 飲料: 原価75円、販売130円、長期保存
- アイス: 原価110円、販売180円、長期保存
- おでん/パン/おかし/デザートは同じ商品マスタの枠組みで個別値を設定。

## 6. 来店客・販売

### 6.1 顧客生成
- 営業時間中、時間帯×曜日×広告×評判×店内魅力で来店希望率を計算。
- 来店希望（potential customers）と**実来店**（入店成功）を分離。入口/レジ混雑で離脱した客は失客として記録。
- **広告効果は逓減**: 比率は上限付きのテーブル/関数から取得。広告費を増やしても常に利益が増えるとは限らない。MVPは広告費 0/1000/2000/5000/10000円/日、来店倍率 1.00/1.10/1.18/1.30/1.40（全て例示）。変更は翌日適用で、適用日の開始時に一回だけ請求する。
- 乱数は再現可能なseedを設け、テストでは固定。来店・購買は上限（処理負荷）のあるモデルとする。

### 6.2 顧客ステート
SPAWN → CHOOSE_SHELF → WALK_TO_ACCESS_TILE → INSPECT → PICK_ITEM → (次の棚 or QUEUE_REGISTER) → PAY → EXIT。
- 目的棚が到達不能/品切れの場合は再探索または諦める。
- 棚スロット在庫は**会計確定時に販売数量を引く方針**に統一し、客が手に取っている間の予約数を別管理して二重販売を防ぐ。予約時にロット/販売価格/原価を固定し、期限切れロットは予約解除→廃棄が会計より先に実行される。
- 客数が増えても、購買するのは在庫に限る。レジの処理能力で行列/失客が発生する。
- キャラクターは4方向の歩行/待機アニメーションを基本とし、低負荷版は2方向＋ミラーを検証。

### 6.3 レジと会計
- レジに顧客待機キューを持つ。複数レジの追加は設計上対応、MVPは1台でよい。
- 会計成立時にtransaction_idを1件生成し、購入SKU・数量・販売単価・原価・日時・顧客IDを記録。棚在庫/予約の確定と売上加算は同一のゲームイベント。
- 資金の更新、売上、原価、棚在庫の一貫性が崩れる「部分成功」を禁止。
- 客が途中離脱した場合の予約在庫は解放し、売上は立てない。

## 7. 経営・広告・決算

### 7.1 会計指標
- 売上高 = Σ(販売単価×数量)
- 売上原価 = Σ(仕入単価×販売数量)
- 売上総利益（粗利） = 売上高−売上原価
- 粗利率 = 粗利/売上高（ゼロ除算時は0/未定義表示）
- 営業損益（ゲーム簡略値） = 粗利−廃棄原価−広告費−電気代−固定費−人件費。
- **現金の増減** = 会計受取−仕入支払−広告支払−その他支払。仕入支払を粗利計算で再度控除しない。
- 什器購入/撤去による現金支出は設備投資として別集計し、営業利益から二重に引かない。
- 損益計算と現金増減は別の表示として明確に区別。

### 7.2 日次決算
- 日時tickと1日終了処理を分離。売上/販売個数/来店数/入店できなかった客/広告費/廃棄費/粗利/営業損益/現金残高を日次保存。
- 「広告費をかけた日/売上が増えた日」の比較ができる。最低7日履歴。
- 営業中に購入設定変更しても、既に販売確定済みの売上は書き換えない。
- 資金不足の発注/設備購入/広告設定は拒否して理由を表示。

## 8. セーブ・データ境界・テスト

### 8.1 保存
- save_schema_versionを持つJSON（Godotの単純型のみ）。ゲーム状態は店舗構造、配置、商品マスタ参照、在庫ロット、現金、広告、日時、seed、顧客進捗（簡略化可）、履歴を含む。
- 破損保存の検出、セーブ失敗メッセージ、原子的なテンポラリ書込→置換。旧バージョンをローダーで検出。
- ゲームデータの内部IDを安定化。見た目のアセット名やファイルパスを保存の主キーにしない。
- データ定義とスプライトレンダラを切り離し、将来2D/別ビューへ置換可能。

### 8.2 設計境界
- Domain: StoreGrid, FixtureCatalog, ProductCatalog, InventoryLedger, CustomerSimulation, SalesLedger, Advertising, DayEnd.
- Application: GameCommands (place/move/rotate/order/restock/price/set_ad), SaveLoad, deterministic simulation clock.
- Presentation: IsometricRenderer, BuildPalette, Inspector, HUD, ReportDialog, interaction handlers.
- Asset tools: Blender scripts + render manifests。**プレゼンテーション層から直接金銭/在庫を改変しない**。操作はコマンド経由。
- 不変条件の検証とログを実装し、致命的不整合を黙って補正しない。

### 8.3 受け入れ条件・最低テスト
1. 1×2什器を90°回すと占有が2×1、グリッド上でズレず描画される。
2. 重複、壁外、入口塞ぎ、到達不能レジの配置を拒否し、UIで理由を表示する。
3. 棚正面に客が到達でき、棚/客の描画奥行きが正しい。
4. 対応外カテゴリの補充・容量超過・負在庫・重複販売を防止。
5. 発注、棚補充、5個販売、廃棄、日次決算の数量/現金/粗利の帳尻が合う。
6. 広告倍率は設定費用の増加に対して逓減し、来店数の試験をseed固定で再現できる。
7. 入口→棚→レジ→出口を客が通れる。品切れ・満員・経路遮断の失敗動作も定義どおり。
8. セーブ/ロードで配置、方向、在庫、価格、現金、広告、時刻、日次履歴が一致。
9. リアル寄りの什器3種（棚/冷蔵ケース/レジ）は同一投影・照明・タイル規格でレンダリングされる。
10. 自動テストはheadless/unit中心。重要操作のみ小さなシーン/E2E試験。**GitHub Actionsの導入は行わない**（ローカルで検証）。
11. ベンチマーク対象は初期16×12店舗、什器20基、同時可視客30人（暫定）。基準PCと実測を明記し、測定条件を変更して「改善」を主張しない。
