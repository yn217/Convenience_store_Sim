# 経営・在庫・顧客シミュレーション詳細規約 v0.1
更新: 2026-10-22｜対象: Domain/Application。GUIやスプライトに依存しない。

## 0. 目的と不変条件
- UI/描画はゲーム状態を表示するだけ。**商品・現金・売上を変更する処理はDomainコマンドのみ**。
- Qtyは非負整数、金額は円整数、時刻はシミュレーション秒（整数推奨）。
- 全経済イベントに一意の event_id / effective_time / schema_version を付ける。再適用しても二重計上されない設計（idempotency）。
- 初期資金、家賃、経営バランスは後述の**仮設定**。テストで使う数値と調整可能なデータを区別。
- 同じ入力、乱数seed、tick順で同じ結果を再現できること。UIフレームレートに影響されない固定ステップ。

## 1. 営業可否・初期状態
- 新しいゲームは**入口があるがレジのない空の店舗**で開始し、自由配置を許可。
- 設置は構造/入口を壊さない範囲で可能。**レジ未設置時には入口→レジの到達性チェックをしない**。代わりに「レジなし/営業開始不可」を表示。
- 営業開始条件は少なくとも有効なレジ1台、入口→レジと販売可能棚のアクセス到達性、商品が1個以上陳列されたこと。
- レジ配置後はレジ/入口の通行経路を遮断する変更を拒否する。**OPEN・CLOSING中は設備の配置/移動/撤去を禁止**し、時計だけを停止しても解除しない。明示的な閉店要求後、店内客と予約が0になりSETUPへ移行してから設備を変更する。詳細は[実装契約08](implementation/08_RUNTIME_STATE_AND_COMMANDS.md)。
- レジを最後の1台撤去したとき: **営業中は拒否**、営業停止中は許可して「営業不可」に戻す。

## 2. マスタ・在庫状態
- ProductSKU: id / name / category / buy_cost / sell_price / expires_after_seconds (nullable) / demand / base_appeal / visual_id / slot_units。
- StockLot: lot_id / sku_id / purchased_unit_cost / expires_at (nullable) / qty / location {backroom or fixture_instance_id+slot_id}。
- InventoryReservation: reservation_id / customer_id / lot_id / qty / unit_sell_price_snapshot / unit_cost_snapshot / expires_at_reservation。スロット実数のうち available_qty = physical_qty - active_reserved_qty。
- ShelfCapacity: `sum(qty×slot_units) <= capacity_units`; 1SKU/スロットはMVPで固定。バックヤード容量はMVP仮に**無制限**、将来拡張時は明示的ルール追加。
- 補充はStockLotのlocationの移動であり売上・費用イベントを発生させない。複数ロットはFEFO順（期限なしは最後、同期限は入荷順）。
- 期限は「現在時刻 >= expires_at」で失効。失効ロットに予約があれば、**予約解除/顧客の購入予定から削除→廃棄**を同一tickで処理し、期限切れは販売不可。
- 在庫整合: 各lotの`physical_qty >= reserved_qty >= 0`。販売確定でphysicalとreservedを同数減算。離脱でreservedのみ減算。
- 棚を撤去するとき、残在庫をバックヤードへ移せる場合にのみ許可（MVPは無制限）。買物予約が残れば撤去を拒否し、営業停止時に予約解放後処理する。

## 3. イベント処理順（固定tick）
1. ゲーム操作コマンド適用（建設は営業停止中）。
2. 失効予約を解除・在庫期限切れを廃棄。
3. 有効な棚・購入可能qtyをスナップショット。
4. 新来店希望の発生 → 入店可否判定。
5. 顧客AIステート遷移・経路更新・棚予約。
6. レジ待機列処理 → 会計確定/顧客離脱・予約解除。
7. 固定の時間境界イベント（広告請求、日次締め、固定費）。
8. UI用のderived snapshot発行。

**設計注意**：日次締めの境界は、前日最後の販売と日付切替の処理順を固定する。tick長と境界時刻を跨いでも同じ日付に二重計上しない。ゲーム内時間早送り中にもシミュレーションを大きなΔtで1回実行してイベントを飛ばさない。

## 4. 会計/予約プロトコル
### 4.1 ステート
- Customer: SPAWN→SELECT→WALK→INSPECT→RESERVE→QUEUE→CHECKOUT→EXIT、取りやめ時 CANCEL→EXIT。
- RESERVEは棚から物理的には引かず、lot/slotに数量予約。予約成立時に**販売単価と原価をスナップショット**。在庫の表示は物理残数を示す（取置き分は予約としてUIに表示可能）。
- CHECKOUTは唯一の販売確定点。作成した transaction_id を軸に予約の検証→在庫確定→売上/原価/現金を**原子的に**更新する。
- 支払いが失敗/売場閉鎖/離脱した場合、予約だけ取り消す。売上・原価は増えない。
- 会計中にロット期限切れになる場合は期限切れが優先し、販売対象から削除して明細/支払額を再計算する。
- 何も買わずに出店する顧客を扱い、顧客数と購買客数を別計測。

### 4.2 円建ての仕訳イメージ
以下は**ゲーム内簡略会計**（実際の税務会計を厳密再現しない）。
| イベント | 現金増減 | 在庫数量 | 売上高 | 売上原価 | 別費用 |
|---|---:|---|---:|---:|---:|
| 100円×10個仕入 | −1,000円 | バックヤード+10 | 0 | 0 | 0 |
| 5個を棚へ補充 | 0 | バックヤード−5、棚+5 | 0 | 0 | 0 |
| 150円×3個販売 | +450円 | 棚−3、予約−3 | +450円 | +300円 | 0 |
| 期限切れ2個廃棄 | 0 | 対象位置−2 | 0 | 0 | 廃棄損失+200円 |
| 広告1日1,000円 | −1,000円 | 変化なし | 0 | 0 | 広告費+1,000円 |
- 上例の粗利=450−300=150円、広告と廃棄損失だけ含めた簡易営業損益=150−200−1000=−1050円。仕入支払1,000円をさらに利益から控除しない。
- 什器購入代金は設備投資（現金支出）。MVPでは減価償却をしないため簡易営業損益から控除せず、**現金残高は大きく変わる**と明記。
- 売上確定・仕入・広告支出・廃棄の各コマンドはevent_id単位で一度だけ適用。

## 5. 需要・客数と売れやすさ
**MVPの調整可能な仮モデル**：
- 1日来店希望数の期待値 = base_traffic(time, weekday) × ad_multiplier(ad_tier) × reputation_multiplier × assortment_multiplier。
- 広告倍率のテーブル（初期仮値）: 0円→1.00、1,000円→1.10、2,000円→1.18、5,000円→1.30、10,000円→1.40。広告1万円で来店が無制限に増える設計にしない。
- 商品購入候補の重み = category_preference × availability × price_attractiveness × placement_accessibility × appeal。正規化して抽選。商品の在庫がなければ重み0。
- 価格魅力度例（仮） = clamp((reference_price / sell_price)^elasticity, 0.3, 2.0)。0円、負数を拒否。売価高いほど購入確率が下がる可能性を表現。
- 品揃え乗数例（仮）= 0.75 + 0.25×min(1, stocked_categories/8)。カテゴリ数だけの購買水増しではなく需要計算に限定。
- 評判: 0〜100、初期50。欠品・レジ待ち・来店時の商品選択成功率などから日単位で微増減。設置レイアウト/品揃えを通じ改善する動機にする。
- 売上/来店 = 購買率×平均買上金額。**潜在来店・実来店・購買客・購入個数・逸失客を別指標**に分ける。
- （#128）1来店は1〜4点のかご（1点40/2点35/3点20/4点5%）。来店数は100→50に半減し、購入点数（平均約1.9点/来店）で販売規模を保つ。会計は20秒＋1点8秒。客単価 = 売上 ÷ 購入客数。
- 全係数はデータテーブル化し、調整可能。ランダム変動を独立乱数ストリーム化（来店、品目選択、ビジュアル演出）し、UI演出変更が売上乱数を変えない。

## 6. 広告と日付境界
- プレイヤーが広告予算を変更しても**翌ゲーム日から**適用する。今日の広告費を日中に上書き・重複請求しない。
- 毎ゲーム日開始の1回の広告費請求で当日の適用ティアを確定。資金不足の場合、適用ティア0円へフォールバックして警告。
- 日次費用（固定費/電気代）も日境界に1回だけevent_idで計上。1日目の費用起算時刻はチュートリアル初日スタート時刻で決定。
- 停止・ロード・時間4×で広告/日次イベントの二重請求が発生しない。

## 7. 日次集計と経営評価
- 売上高、販売個数、売上原価、粗利、廃棄損失、広告費、光熱費、固定費、簡易営業損益、設備購入支出、当日現金増減、期末現金。
- 来店希望数、実入店数、購買客数、買わずに退出、行列断念、売切れ発生数、平均買上金額、棚売上。
- 0件時は平均値・率を「—」か0として統一し、NaNやInfinityを出さない。
- 現金マイナスを許さないMVPルール。資金不足は購入/広告予約操作拒否。現金不足で営業費用が賄えない場合は**ゲームオーバーではなく支払い不能状態**で一時停止して救済/再挑戦誘導（詳細は GAMEPLAY_UX_SPEC）。
- 在庫評価額 = Σ各lotの購入原価×physical_qty（消費/廃棄によって変化）。
- 指標の計算コードは表示する画面と独立させる。

## 8. セーブと復元（MVP）
- save_schema_version, store, fixture_instances, inventory_lots, active_reservations or safe_resume_checkpoint, product_price_overrides, cash, ad_budget_next_day, applied_ad_tier_today, game_tick, day_closing_marker, random_stream_states, daily_ledger, applied_event_ids を保存。
- **MVPでは営業中セーブを許すが安全境界で確定**: 1 tick処理完了後に原子的スナップショットを生成。復元後は顧客・予約の整合を維持するか、保存時点で店内客を安全に退場・予約解除したチェックポイント形式のどちらかを選び、実装時に仕様テストを追加する（推奨: 同じ顧客/予約を復元）。
- 保存の整合性は現金、販売済取引ID、棚在庫、予約数、費用締めマーカーで検査。
- 壊れたファイル/未知バージョンは読み込み拒否し、利用可能な旧セーブを壊さない。
- UI/描画のスプライト枚数や派生LOD状態は保存しない。
